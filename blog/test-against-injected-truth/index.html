Test your pipeline against injected truth before you touch real data

Oct 21, 2026 · 2 min read
  • testing
  • synthetic data
  • uncertainty
  • pytest

Real Earth-observation data has no answer key. If a calibration pipeline reports that Landsat 9 reads 0.35% brighter than Landsat 8, is that the sensors, or a bug? If a canopy-height model's 90% intervals cover 90% of the data, is the conformal code right, or did a leak make it look right?

My habit is to answer those questions before real data exists, by building a synthetic backend that shares the real backend's data contract but injects known truth.

How it works

In my Landsat 8/9 cross-calibration pipeline, the science code doesn't know where its data comes from. One backend pulls real scenes from Google Earth Engine. The other generates scenes with a fixed, known inter-sensor bias and a known sub-pixel shift, plus realistic noise.

A pytest suite then asserts the pipeline gets the answer back:

Quantity Injected Recovered
Red-band bias +0.353% +0.355%
Thermal band bias −0.188 K −0.190 K
Geometric shift (dy, dx) (+0.35, −0.20) px (+0.32, −0.18) px

If those tests pass, a surprising number on real data is a finding, not a bug.

The part people skip: score the test bed afterwards

For my canopy-height project I ran the full analysis on a synthetic landscape before pulling real GEDI data, then compared. The scorecard was humbling:

Synthetic prediction Real data Verdict
Random CV 6–11% optimistic vs spatial 2–3% Direction held, size didn't
R² ≈ 0.8 R² 0.32–0.40 Far too optimistic
Tree models beat ridge by 20–25% Within 3% Wrong
Transfer is the dominant error 34–45% worse Held
Dropping elevation helps transfer 9–20% better Held, more strongly
Conformal intervals hit nominal within regions 0.902 Held
Coverage breaks under transfer 0.56–0.78 Held, worse on real data

The test bed was right about the machinery: folds, buffers, conformal calibration, and the failure modes. It was wrong about accuracy, because my simulator gave imagery far more height signal than reality does.

That's the correct division of labour. A synthetic test bed tells you whether your code measures what you think it measures. Only real data tells you how good the model is. Mixing those up, in either direction, is how pipelines ship with silent bugs or with overconfident accuracy claims.

The checklist

  1. Separate the data source from the science code behind one data contract.
  2. Build a synthetic backend that injects known values for every quantity you estimate, including the uncertainty.
  3. Write tests that recover the injected truth within the stated noise.
  4. Label synthetic results as synthetic, everywhere they appear.
  5. After real data arrives, publish the comparison, including what the simulator got wrong.
